# テストの追加と見直し

SPEC: Issue #40。テスト群の肥大化を抑えるための規則。

## テストを追加・変更するとき

1. 新しいケースを足す前に、既存のケースまたは fixture を拡張して同じ確認ができないかを検討する。回帰テストは、既存のテストに assert を足すことでもよい。
2. 新しいケースにする場合は、その理由を PR に書く。
3. 重い準備（Git リポジトリ・受信側など）は、モジュール内で1回だけ作って、テストごとに複製する。複製では次を守る。
   - remote URL など、絶対パスを持つ設定を付け直す
   - 偽の scanner と環境変数（`PATH` 等）はテストごとに作り直す（`setUpTools()`）
   - 複製元の中に worktree を作らない（絶対パスが記録されるため）
   - 複製のあとに、origin と remote-tracking ref が正しいことを assert する
4. 本番のスクリプトの待ち（`sleep`、timeout）は変えない。テスト側で、呼ばれたことを記録してすぐ終わる偽のコマンドを `PATH` に置くか、独立した待ちを並行させる。
5. 公開前検査、pre-push、installer の拒否テストは、統合・高速化で assert を減らさない。統合・高速化で変えてよいのは fixture の作り方だけ（assert の追加は 1. のとおりよい）。

## 統合・変更したテストで失われる確認がないことを示す

1. 統合の前後で、ケースの一覧（subTest・ループの各ケースを含む）を機械的に比べる。
2. 区別される assert ごと（または統合したテストごと）に、対象のスクリプトをわざと壊した版を用意し、どの assert が FAIL するかを統合の前後で記録する。
3. fixture を複製に変えた箇所は、複製の手順を壊した版（remote URL の付け直しを省く、状態をテスト間で共有する等）でもテストが FAIL することを確かめる。
4. 結果を PR に書く。

## 見直しのきっかけ

- CI の `step-times` ジョブが、工程ごとの所要時間を毎回 `$GITHUB_STEP_SUMMARY` に表示する（`tests/ci-step-times.py`）。閾値を超えても CI は失敗しない。
- きっかけ（どちらも仮の値）:
  - テスト工程の所要時間の合計が70秒を超えた
  - 1工程が15秒を超えた
- checkout・apt・Gitleaks の取得など、ネットワークに左右される準備の工程は合計に含めない。
- `tests/` を変える PR では、Root が表示を読み、超えていれば見直しの Issue を作る。
