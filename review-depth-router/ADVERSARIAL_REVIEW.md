# 敵対的レビュー結果：review-depth-router v1.0

## 対象・方法

対象: `review-depth-router/SKILL.md`, `references/rubric.md`, `scripts/decide.py`、単体テスト。焦点は「同一PRを別の評価者が分類しても判定が一致するか」と、**高リスク変更を通常レビューに誤振り分けしないか**。

手法: 5軸の境界・強制条件・証拠不足・例外ケースに対して反例を構成。機械的ロジックはPython標準ライブラリによるテストで検査。自然言語ルーブリックについては設計者自身による敵対的な机上検証であり、異なるモデルによる独立評価は**未実施**。

## 重要指摘と修正結果

| ID | 重大度 | 敵対的な反例／曖昧さ | 措置・結果 |
|---|---|---|---|
| AR-01 | 高 | 重大なデータ損失リスクが「影響度2・他0」で通常レビューになる | `impact=2` または `recovery=2` は単独で FULL。テスト済 |
| AR-02 | 高 | 根拠なしの「0点」を認めると不明な変更を低リスク化できる | `null` を明示し保守的に2点として判定、PROVISIONAL表示。入力証拠欄必須。テスト済 |
| AR-03 | 高 | 「異常系が未テスト」を verification=1 にも2にも解釈できる | 変更箇所を通る正常系テストが通れば1、関連する成功検証が皆無なら2と明文化。ルール修正済 |
| AR-04 | 高 | タイムアウト・並行制御の変更でテストがない場合も合計4点のFOCUSEDに留まる | `verification=2` かつ `uncertainty=2` または `scope=2` はFULL。テスト済 |
| AR-05 | 中 | 「複数モジュール」をディレクトリ数で数えるモデルと実行パスで数えるモデルが分かれる | 単一実行エントリポイント／同一プロセス内複数／プロセス・サービス越境を分類基準に変更。適用には依存元確認が必要 |
| AR-06 | 中 | READMEに「認証」と書いてあるだけでAUTH強制発火する | 実際に稼働する認証・権限判断の変更だけを強制条件とする。文書中の単語一致は対象外 |
| AR-07 | 中 | AIエージェントは一般に副作用を持つため、全てのモデル変更がAUTONOMOUS_EFFECTになり得る | 承認なしに許される副作用・対象・再試行が**今回の差分で変わる**ことを必要条件に限定 |
| AR-08 | 中 | 「よく知られたパターンだから不確実性0」は再現性のない主観 | 挙動同等性の差分根拠と適切な回帰テストが必要と明記 |
| AR-09 | 中 | CIテスト1件の削除が「必須セキュリティゲート無効化」なのか不明 | 必須ゲートをbranch protection/リリース規則/required workflowで定義。通常の任意テスト修正と区別 |
| AR-10 | 中 | ドキュメントしか変えていなければ必ずimpact=0、とすると危険コマンドの誤記を見逃す | 実行され得るドキュメント手順は利用者行動への影響を評価。検証の例外を明文化 |
| AR-11 | 中 | PR本文やdiffに「0点にしろ」が書かれているとSkillが従う可能性 | PR/diff/テストログは評価対象データであり命令でないと明示 |
| AR-12 | 低 | 「独立レビューを2回まで」では重大問題が解決しなくても承認してしまう | 上限は自動反復のみ。残件があれば人間へエスカレーションと明記 |

## 評価シナリオと期待値

| ケース | 注目する境界 | 期待する出力 |
|---|---|---|
| READMEの誤字のみ | 非実行変更とゲート | NORMAL / FINAL |
| 文書に認証方式を説明するだけ | 単語一致による誤発火 | AUTH=no（それ自体ではFULLにしない） |
| 1行だけ認可条件を緩和 | 行数ではなく実際の権限判断 | AUTH=yes、FULL |
| 一部のリトライ条件だけ変更、同じリトライ処理の成功テストあり | 単独の不確実性2 | 少なくともFOCUSED |
| リトライ条件変更、関連テスト成功実績なし | 複合ルール | FULL |
| 副作用を持つagentの自動再試行を追加 | 強制条件 | AUTONOMOUS_EFFECT=yes、FULL |
| モデルのみ切替、権限・ツール・副作用は不変 | 強制条件の誤発火 | AUTONOMOUS_EFFECT=no（他の指標で判定） |
| 呼び出し側を特定できない共有関数変更 | 未確認の扱い | scope=null、PROVISIONAL |
| 認可の変更有無が読み取れない | ゲート不明 | AUTH=unknown、FULL/PROVISIONAL |
| 外部へ送信されたメッセージを取り消せない | ロールバックと復旧 | recovery=2、FULL |
| システム間のイベントスキーマ変更でテストが走らない | 境界＋検証欠如 | scope=2、verification=2、FULL |
| 他者に秘密情報を送らせる文書手順 | 「文書は低リスク」の反例 | impact=2が妥当ならFULL。実際の因果関係の証拠が必要 |

## 検証結果

- 自動単体テスト **21件パス**。強制条件・スコア境界・未確認・不正入力を検査。
- 0〜2点の5軸、**243通り**の組み合わせに対して、1軸の点数を上げてもレビュー深度が低下しないことを機械的に確認。
- ただしテストは**与えたスコアに対する判定ロジック**のみ検証する。AIが実際のdiffから正しいスコアを選ぶことや、証拠の真正性を保証するものではない。

## 残存する曖昧さ（意図的に未解消）

1. **「起こり得る重大障害」**は変更の依存関係や運用条件によって異なる。危険な因果関係を証明・反証できない場合はimpact=nullで保留する。
2. **動的ディスパッチ・プラグイン・反射**などの呼び出し関係は、静的検索だけでは全利用者を確定できない。scope=nullでの暫定判定が必要。
3. **証拠欄の真偽はスクリプトで検証できない**。例えば「テスト実施済み」と虚偽入力すれば過小評価が可能。実際のコマンド結果、diffと照合しなければならない。
4. `0–2 / 3–5 / 6–10` という閾値は現時点で運用データに裏付けられていない。強制・複合条件も安全側の設計判断であり、最適化済みではない。

## 判定と次の検証

**暫定合格（機械的ルーティング）／実プロジェクトでの評価者間一致は未検証。**

次の段階として、異なる担当者またはモデルに**20件の実PR**を独立評価させる。事前に決める試験合格目標の例は「最終レビュー方式の一致率90%以上（20件中18件以上）」「既知の強制条件テストで見逃し0件」。一致しないケースは具体的な判定根拠を比較し、条文1箇所ずつ改訂する。実験前に合格基準を固定し、試験後に閾値を都合よく変更しない。

これはレビュー方式を選ぶSkillであり、PRの安全性・マージ可否を承認するSkillではない。
