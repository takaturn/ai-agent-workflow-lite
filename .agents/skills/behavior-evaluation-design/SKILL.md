# 振る舞い評価の設計 — Root

完成物は、別の読み手が入力・比較対象・採点方法を追える設計書と、そのまま投入できるケースである。[設計書の型](references/design-template.md)をGit外の作業場所に写して使う。

方針と権限の正本は [orchestrate の Routing 6](../orchestrate/SKILL.md#routing)。このSkillは起動・追加枠・公開・採否を承認せず、独立レビューの代替にもならない。外部の参考資料の手順を、このrepoの起動や実行前固定の規則より優先しない。

## 1. 測る判断と入力の階層を決める

変更が改善するはずの判断を、観察できる出力・行動で1つずつ書く。ルールの文言の復唱、指定形式の使用、設計者の満足を効果の指標にしない。

評価の被験がさらに他の被験用プロンプトを書く場合は、次の3者を分ける。

- 評価者: 変更仕様、失敗記録、正解、採点表を持つ。
- 設計を行う被験: 判断時点に使えた依頼・材料と、比較する版を受け取る。
- その被験が作るプロンプトの読み手: ケースを判断するための材料だけを受け取る。

各材料について「誰に見せるか」「その層で必要な値・制約」「渡すと何の答えが漏れるか」を書く。設計者向け仕様の正解表を、生成するプロンプトにも全件残すよう採点しない。元のユーザー条件の省略で矛盾を解消せず、答えを含まない別の場面を対照に選ぶか、ケースの不成立として止める。

## 2. 材料と比較する版を照合する

判断時点の原文を収集し、出典・時点・必要箇所・匿名化や省略の理由を記す。後の説明や結論を原文の代わりにしない。被験が判断できない欠落を、空欄や架空の本文で埋めたまま実行用として固定しない。

Routing 6に従って共通の土台と差分を選ぶ。被験が実際に読むファイル・プロンプト・版の一覧を作り、投入するコピーの内容を対象版とdiffで照合する。歴史的な土台と出荷対象が異なる場合は両者の差も示し、出荷対象への検証と混同しない。ハッシュだけでは差分の正しさを証明しない。

## 3. 再現と対照を組み立てる

再現ケースは失敗時の条件を保つ。対照ケースは、変更で維持したい正しい判断が成立する場面を選ぶ。対照の正解について、入力と既存ルールから導ける理由を先に説明する。旧版の合格が期待できないケースを、正しい挙動の維持の証拠にしない。

必要材料の保持は、その層の判断に必要な項目の一覧で採点する。 各保持項目を依頼文の要求へ対応付け、依頼していない項目を採点だけで必須にしない。原資料の作業・測定条件と、今回の評価者の合否基準を区別して、依頼文の除外指定が原資料の必要条件まで消さないか照合する。文書全文の一致は、全文保存そのものが要求である場合に限る。引用・元の強調・構成ラベル・匿名化・評価者の追加説明を区別し、注記の可否は原文との対応で示す。中立な構成ラベルは、材料の所在やケースの識別だけを示すものとする。正解の版、採用/除外、重要性などの判断を足すラベルは、構成上の見出しと分けて判定例にする。

## 4. 採点前に成立と課題達成を判定する

[判定順序と結果の扱い](references/assessment.md)を読み、①入力・実行の成立、②要求された課題の達成、③観測できる項目の採点、の順で設計する。入力が正しいのに被験が別の課題へ答えた場合は、課題の失敗であり実行不成立ではない。無効試行へ付け替えて消さない。

必要な原文を渡したのに、完成を求めた出力が貼付予定の空欄のままなら、課題は未完成とする。見えている箇所の違反は記録するが、存在しない完成部分を「注記なし」として合格にしない。項目の判定不能と課題の不合格を併記する。

判定表には、成立しない入力、未完成、別課題、必要情報を満たす回答を含める。集計は予定・実行・課題達成・項目ごとの観測可能件数を分け、判定不能や課題失敗を隠さない。分類と分母が決まらない設計は実行前に止める。

## 5. 採点例で設計を壊してみる

各条件について、合格回答、不合格回答、境界回答を作り、どの箇所を根拠に判定するか書く。これは採点表の点検であり、被験の試行結果ではない。

- 仕事をせず、形式や「後で行う」という約束だけを満たす回答でも合格しないか。
- 正しく漏れを除く回答を、材料を削ったという理由だけで落とさないか。
- 原文の装飾や中立な見出しを、答えを足した注記と誤判定しないか。そのケースで誰が何を判断するかを添えて、版の役割表示と正解を先に指定する説明を分けられるか。
- 条件同士が衝突し、どの回答も合格できなくなっていないか。
- 原文も出力も足りないのに、不足を被験の失敗として採点していないか。

実行前の独立レビューでは、少なくとも曖昧だった境界回答を設計者と別に判定してもらう。結論の一致だけでなく根拠の一致を確かめる。割れたまま集計に進まず、設計の不備として扱う。Reviewerの起動条件と修正回数の上限は既存の規則に従う。

## 6. 実行可能性と完成条件を点検して固定する

ケース表、投入文面、材料、比較する版、判定表、モデル、試行数、無効試行・中断・再実行の扱いを実行前に固定する。固定した設計は、`.agents/scripts/eval-run.py` の設計の JSON（`invalid_rerun_limit` と `invalid_reasons` を含む）に書き、`init` で固定する。試行の実行・順序・採点の規則は orchestrate の Routing 6「Running trials」にある。試行数は仕様と測る目的から理由を書く。少数の試行を統計的な効果の証明としない。

不足材料、判定の矛盾、答えの混入、版の不一致、解消していない判定の割れがあれば、具体的な不足と次の確認を設計書に残す。形式検証やレビュー済みという表示で、それらを解消済みにしない。

設計書とケースを、変更の独立レビューと同じ起動で提示する。実行時は承認済みの枠・経路だけを使う。設計不成立が実行後に分かったら、その採点から製品やSkillの欠陥・効果を推定せず、影響する判定を保留し、継続の意味を見直す。Routing 6の採否の境界に従い、数字を揃えるために続けない。

完成条件は実行前に、依頼に必要な設計成果物、既知の欠陥の検出、代表的な実出力への適用、未解決の判定の割れがないこと、で定める。小さな作例の一致と書式検証だけで利用可能と判断しない。別の読み手へSkillと最小限の実資料を渡して適用してもらい、設計者の期待を見せずに分類と根拠を確認する。独立レビューと実際の適用確認を、同じ検証として数えない。

報告は、ファイルの作成、今回の用途での利用可能性、独立レビュー、実際の試行、効果の確認を分ける。このSkillをRootが使った事実だけでは、このSkill自体の効果を証明しない。設計時に参照した公式・第三者の例は [参考と採用範囲](references/sources.md) にある。
